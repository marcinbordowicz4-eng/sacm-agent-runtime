# SACM Agent Runtime 0.2.0

Version 0.2.0 promotes SACM from an orchestration MVP to a secure, auditable
software-delivery control plane. The complete feature summary is in
[`CHANGELOG.md`](../../CHANGELOG.md).

## Benchmark status

Benchmark 100 is **IMPLEMENTED, NOT_RUN**. The checked-in 100-case suite and
pinned fixture manifest validate structurally, but no external model or SACM
executor run is included. `NOT_RUN` is not evidence of product quality,
performance, security, cost efficiency, or superiority.

## Upgrade and migration

1. Back up PostgreSQL and artifact/evidence storage, then complete a restore
   rehearsal.
2. Stop writers and drain active runs and customer-executor leases.
3. Install the 0.2.0 wheel or image by verified digest.
4. Run `sacm-migrate` once with the production `DATABASE_URL`. The expected
   single Alembic head is `c8d1e4f7a2b5`.
5. Run the tenant backfill for legacy nullable rows and review unmatched
   records before enabling strict tenant enforcement.
6. Update customer-executor configuration to version `0.2.0`, verify signing
   and mTLS pins, then re-enroll identities only when those identities changed.
7. Verify OIDC/service credentials, fail-closed OPA, evidence/job signing,
   secret brokerage, remote workflow execution, executor capabilities and
   regions, audit export/SIEM delivery, backups, and readiness probes.
8. Resume traffic gradually and retain the pre-upgrade backup and artifacts
   through the rollback window.

Database downgrade is not the rollback mechanism. If rollback is required,
stop 0.2.0 writers and restore the pre-upgrade database and artifact snapshot
before deploying the prior application version.

## Release gate

`python scripts/release_check.py --version 0.2.0 --dry-run --allow-dirty`
runs the local checklist. It intentionally exits with an `INCOMPLETE` blocker
when a passing signed `security-release-evidence` artifact for the current
commit is absent. Never waive or reinterpret that result.

The tag workflow also requires a successful `Security release gate` workflow
artifact for the exact tagged commit. It builds and tests Python and Mission
Control, validates the wheel, creates SPDX SBOM and provenance attestations,
signs release checksums, builds Docker, optionally pushes GHCR when
`PUBLISH_GHCR=true`, and creates or updates the GitHub Release. PyPI upload is
disabled unless both `PUBLISH_PYPI=true` and `PYPI_API_TOKEN` are configured.

## Maintainer release sequence

Do not create the tag until the release commit is on `main` and both CI and the
security release gate have passed for that exact commit:

```bash
git add -A
git status --short
git commit -m "Prepare release v0.2.0" \
  -m "Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>"
git push origin main
sha="$(git rev-parse HEAD)"
ci_run="$(gh run list --workflow ci.yml --commit "${sha}" --limit 1 \
  --json databaseId --jq '.[0].databaseId')"
security_run="$(gh run list --workflow supply-chain.yml --commit "${sha}" --limit 1 \
  --json databaseId --jq '.[0].databaseId')"
gh run watch "${ci_run}" --exit-status
gh run watch "${security_run}" --exit-status
git tag -s v0.2.0 -m "SACM Agent Runtime v0.2.0"
git push origin v0.2.0
release_run="$(gh run list --workflow release.yml --commit "${sha}" --limit 1 \
  --json databaseId --jq '.[0].databaseId')"
gh run watch "${release_run}" --exit-status
gh release view v0.2.0
```

Wait for each run to appear in `gh run list --commit "${sha}"` before resolving
its ID. Before tagging, confirm both `CI` and `Security release gate` succeeded
at the exact SHA. The release workflow creates the GitHub Release; do not run
`gh release create` manually unless recovering a failed workflow after
reviewing its uploaded artifacts.
